# Внешние аккаунты Telegram

Этот провайдер использует пользовательский аккаунт Telegram через MTProto. Настройте клиентское приложение на сервере, затем выполните аутентификацию из диалога внешних аккаунтов с помощью QR-кода и, если включено, пароля двухэтапной верификации Telegram. Одних учетных данных приложения недостаточно для авторизации пользовательского аккаунта.

## Конфигурация

Независимый процесс `workspace-telegram` читает тот же файл конфигурации, что и API. Если ID приложения не задан, это отключает провайдера. Платформа генерирует отдельный ключ шифрования; сохраняйте его вместе с резервной копией базы данных. Существующие зашифрованные сессии нельзя восстановить без соответствующего ключа.

```ini
[telegram]
api_id = 0
api_hash =
secret_encryption_key =
history_batch_size = 100
poll_interval = 1
```

Поместите учетные данные приложения в управляемый оператором файл переопределения `/etc/workspace/telegram.conf`, доступный только root. API и демон читают этот файл после основной сгенерированной конфигурации. Храните переопределение в отдельном ресурсе конфигурации платформы, ориентированном на узел бэкенда, при этом хеш приложения должен предоставляться через ссылку на секрет платформы; обновления элементов не должны владеть этими учётными данными или сбрасывать его. Используйте хранилище секретов платформы для учетных данных. Никогда не помещайте сессии аккаунтов, токены входа, пароли или хеши приложений в публичные настройки внешних аккаунтов, сообщения, логи или клиентские кэши. Ответы аутентификации API ограничены владельцем и проектом, никогда не кэшируются и исключаются из журналирования тела ответа даже на уровне DEBUG.

## Контракт аккаунта и аутентификации

Создайте внешний аккаунт с помощью `provider=telegram`. Публичные настройки пусты: все доступные диалоги и их полная история импортируются автоматически. Устаревшие входные данные `history_depth`, `selection_mode` и `peer_keys` отбрасываются. Идентификатор провайдера — фиксированное имя хоста Telegram. Существующий маршрут внешнего аккаунта и значения статуса остаются доступными для старых клиентов.

Владелец вызывает следующее действие, используя существующее разрешение на обновление внешнего аккаунта:

```text
POST /v1/messenger/external_accounts/{uuid}/actions/telegram_auth/invoke
{"operation":"start"}
{"operation":"status"}
{"operation":"password","generation":"attempt-uuid","password":"example-only"}
{"operation":"cancel","generation":"attempt-uuid"}
```

Попытка входа истекает через пять минут. QR-токен обновляется в рамках этой попытки. Закрытие формы отменяет только ее текущую генерацию; старая форма не может отменить более новую попытку. Пароли шифруются, потребляются один раз и истекают вместе с попыткой. Демон отзывает авторизацию, завершенную после отмены. Удаление аккаунта отключает синхронизацию, отвязывает членства владельца и запрашивает выход из Telegram перед удалением корневого аккаунта и его зависимого состояния.

## Синхронизация и идентичность

Каждый аккаунт имеет одно соединение и блокировку advisory lock в PostgreSQL. Демон выполняет различия в прямых/групповых чатах, сверку каналов, повторную загрузку медиа, обновление каталога и исходящую доставку как отдельные задачи. Приватные диалоги, базовые группы и каналы независимо выполняют один и тот же цикл истории, поэтому большой файл канала не может отложить первую страницу истории приватного или группового чата. Срок повторной попытки GetHistory для них общий и проверяется перед каждым собеседником; статус аккаунта остается «синхронизация», пока все выбранные истории не завершатся. Telegram и Zulip разделяют этап staging COPY, слияние контента/корня/размещения/привязки на основе наборов, сверку личных флагов и планирование счетчиков. Полученные страницы Telegram сохраняются перед слиянием; удаление страниц и контрольные точки фиксируются вместе с канонической партией. Оба импортера уступают место потоковым данным и очереди публикаций. История не отправляет одно событие websocket для каждого импортированного сообщения. Страницы, содержащие только служебные данные, все равно продвигают контрольную точку. История всегда читает все, что Telegram делает доступным для этого аккаунта. Каталог обновляется каждые 60 секунд. Неизвестный прямой/групповой диалог в общих различиях обновлений немедленно пробуждает ту же задачу каталога, поэтому его начальная история не ждет периодического таймера; сообщения в известных диалогах не запускают повторное сканирование. Контакты, собеседники диалогов и авторы сообщений становятся стабильными пользователями Telegram в каталоге Workspace. Проверенные профили IAM остаются авторитетными.

Приватные диалоги и сообщения базовых групп используют идентичности в рамках аккаунта. Идентичности сообщений каналов и супергрупп разделяются в рамках проекта и провайдера. Потоки Telegram сохраняют доступ Workspace, ограниченный членством. Личные папки содержат прямые диалоги; каналы Telegram и базовые группы появляются в разделе «Каналы» независимо от этого флага доступа. Потоки Telegram — это приватные потоки Workspace; исходный аккаунт другого пользователя должен независимо импортировать тот же канал, прежде чем этот пользователь получит членство. Обычные чаты используют тему по умолчанию `telegram`; ответы в форумах сохраняют свою исходную тему. Разговоры Zulip без исходной темы используют `zulip`. Веб-клиент группирует видимые незашифрованные прямые потоки только по точному UUID собеседника Workspace, проекту и зрителю. Каждая тема провайдера сохраняет свой физический UUID потока для доставки и авторизации; нативные темы используют существующий канонический нативный прямой поток. Имена, адреса электронной почты и имена пользователей никогда не объединяют идентичности. Периодическая сверка каталога повторно использует тот же писатель потоков для обновления существующего собеседника в прямом чате после проверенной привязки аккаунта; она сохраняет физический разговор и не предоставляет членства новому привязанному пользователю.

Эхо реакций повторно использует канонический ключ сообщения/пользователя/эмодзи и сохраняет существующий UUID реакции Workspace; повторяющиеся обновления источника и последующее удаление не создают второй факт. Надежный входящий ящик изолирует снимки источника от более новых обновлений. Пробел в журнале источника запускает авторитетное повторное сканирование истории; покрытые диапазоны страниц сверяют удаленные сообщения, не удаляя более новые поступления. Исходящие отправки сохраняют случайный идентификатор перед удаленной записью и используют авторитетные квитанции. Ранние эхо собственных сообщений ждут во входящем ящике, пока их квитанция не привяжет исходный UUID Workspace. Неопределенный дублирующийся идентификатор остается явной ошибкой, а не коррелируется по тексту сообщения.

Текст, временные метки источника, ответы, отдельные фото/документы, редактирования, удаления, обычные эмодзи-реакции и подтверждения прочтения владельцем используют канонические сущности Messenger. Чтение только для исходных чатов отклоняет отправки. Секретные чаты, звонки, истории, платежи, управление участниками, пользовательские эмодзи и исходящие альбомы с несколькими вложениями находятся вне текущей реализации. Telegram может накладывать дополнительные лимиты на сообщения, файлы, реакции или частоту запросов; ожидания при флуде сохраняют надежную контрольную точку и срок повторной попытки.

## Измерения и приемка

Статус аутентификации включает начало истории для каждого чата, первое зафиксированное сообщение, завершение, количество импортированных сообщений/файлов/байтов, время получения истории, время слияния и время подготовки. Пропускная способность — это импортированные сообщения, деленные на прошедшее время; объем файлов и паузы, назначенные провайдером, указываются отдельно. Эти локальные счетчики не доказывают доставку в Telegram.

Приемка должна записывать фактические исходные и развернутые артефакты, авторизацию по QR, полный доступный охват чатов, холодный импорт, повторное воспроизведение, восстановление после перезапуска, задержку в реальном времени во время импорта истории, равенство байтов вложений на обоих концах и проверки отказа в доступе. Проверьте нативную отправку сообщений и свежий трафик Zulip в обоих направлениях после финального перезапуска. Держите синтетические/локальные временные показатели отдельно от измеренных результатов живого Telegram.

## Примеры преобразования сообщений

[Открыть офлайн-сравнение Telegram ↔ Workspace](../telegram_messages_preview.html). Его синтетический вид Telegram иллюстрирует сущности MTProto, а не воспроизводит клиент Telegram. Workspace использует свой фактический рендерер и тему. Те же примеры JSON проверяются на соответствие рабочему преобразованию в модульных тестах; генератор также проверяет семантику отрендеренного DOM.

Запустите `node workspace/tests/fixtures/render_zulip_messages_preview.mjs --telegram` с локальными копиями UI Workspace и исходного кода Zulip. `WORKSPACE_UI_SOURCE_DIR` и `ZULIP_SOURCE_DIR` переопределяют их пути. Общий генератор сохраняет существующую страницу Zulip.

Сущности Telegram становятся экранированным CommonMark: жирный, курсив, зачеркнутый, спойлеры, код, блоки с указанием языка, помеченные ссылки и цитаты. Смещения UTF-16 сохраняют текст вне BMP. Исходящий CommonMark Workspace парсится в текст/сущности MTProto, а не в несовместимый устаревший Markdown Telethon. Подчеркивание в настоящее время сохраняет обычный текст, так как в Workspace нет синтаксиса подчеркивания; это ограничение видно на странице сравнения.

Ссылки на сообщения/цитаты Workspace становятся нативными ответами Telegram, когда их цель принадлежит тому же исходному диалогу. Ссылки на вложения и ответы парсятся как ссылки CommonMark; литеральные примеры внутри кода сохраняются как текст. Неподдерживаемые ссылки только для Workspace сохраняют свою читаемую метку вместо недопустимого URL Telegram.

## Изоляция в реальном времени и права на публикацию

Получение пропущенных обновлений личных и групповых чатов, сверка каналов, надёжная повторная обработка медиа, история, обновление каталога и исходящая доставка выполняются как отдельные задачи аккаунта. Медленный RPC канала или загрузка файла не блокирует цикл получения личных сообщений. Необработанные обновления каналов имеют приоритет для этого канала во время догоняющей синхронизации. Идентичности медиа фиксируются в надежном входящем ящике перед продвижением курсора обновлений; повторная загрузка повторно получает их и переживает перезапуск. Отзыв аутентификации останавливает аккаунт; обычные ошибки истории/каталога сохраняют свою контрольную точку и ограниченный срок повторной попытки. Диагностика статуса раскрывает сроки повторных попыток и типы ошибок без текста исключений провайдера.

Публичная возможность потока `can_send` вычисляется для каждого пользователя на основе членства, политики публикации, разрешений источника и подключенного аккаунта. Записи API отклоняются перед созданием канонического сообщения или задания отправки, когда отправка недоступна. Нативные каналы `announcement_only` позволяют публиковать владельцу, администратору и модератору; только владельцы/администраторы управляют этой политикой и повышенными ролями. Существующий флаг уведомлений о создании `announce` имеет отдельную семантику. Создание только для объявлений в настоящее время доступно для незашифрованных нативных каналов. Каналы Telegram отражают фактические права подписчика на публикацию.

Импортированные идентичности Telegram повторно используют записи внешних аккаунтов без сессии авторизации, как и импорты Zulip. Последующий подтверждённый вход может привязать импортированную идентичность, но не может забрать идентичность, уже подключенную к другому пользователю Workspace. Упоминания разрешаются только через провайдера и проект выбранной темы, включая стабильные импортированные ссылки UUID после привязки аккаунта. Совпадение имени или адреса электронной почты не подтверждает идентичность.

## Режимы уведомлений Telegram

Режимы потоков синхронизируются в обоих направлениях. `all_messages` явно включает уведомления в чате Telegram. `muted` и `mentions_only` оба используют длительное отключение звука Telegram; Workspace сохраняет их различное локальное поведение уведомлений. Эхо того же значения отключения звука сохраняет локальный режим. Последующее эффективное изменение источника отображается на `muted` или `all_messages`. У Telegram нет точных эквивалентов для каждого режима Workspace. Темы `default`, `follow`, `unmute` и `mute` остаются предпочтениями тем Workspace и не переписывают весь чат Telegram.

Начальные настройки диалога и значения по умолчанию Telegram для пользователей/групп/трансляций импортируются с наследованием. Обновления уведомлений без pts обрабатываются отдельно. Ожидающие локальные намерения и временные метки наблюдения предотвращают перезапись более новых локальных предпочтений устаревшими снимками источника. Исходящие изменения устанавливают только `mute_until`, сохраняя настройки звука и предпросмотра. Изменения при приемке должны делать снимок и восстанавливать целевые предпочтения источника.
