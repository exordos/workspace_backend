# Совместимость стикеров с Zulip

## Цель и инвариант

Сообщения Workspace сохраняют каноническое представление Markdown
`![sticker](urn:sticker:<uuid>)`. Zulip получает исходные байты медиафайла через
существующий процесс загрузки и обычную ссылку на вложение с меткой
`workspace-sticker:v1:<uuid>`. Проверенное отмеченное вложение преобразуется
обратно в каноническую ссылку на стикер перед отправкой события в Provider API.

Это не импортирует новые стикеры в каталог. Обычные изображения остаются
обычными изображениями, даже если их байты совпадают с существующим стикером.

## Подтверждённые границы реализации

- Backend: `workspace/external_bridge_control/files.py`,
  `file_repository.py`, `service.py` и подключение runtime в
  `workspace/cmd/external_bridge_api.py`.
- Репозиторий bridge: `exordos/workspace_zulip_bridge`.
- Исходящее преобразование bridge: `zulip_adapter.py`,
  `_convert_workspace_content`; сейчас оно вызывает `export_file`, загружает
  файл через клиент Zulip и изменяет назначение через `link.with_destination`.
  Исходный флаг синтаксиса изображения сохраняется.
- Входящее преобразование bridge: `converter.py` вызывает разрешение файлов из
  `service.py`; `file_api.py` отвечает за аутентифицированные запросы к API
  файлов.
- Provider ingress уже принимает канонический Markdown стикера. Стикеры нельзя
  добавлять в обычную межпроектную проекцию WorkspaceFile: ссылки на каталог
  глобальны и не требуют записей файлов для отдельного чата.

## Контракты обмена

### Исходящие байты

Расширить существующий `PUT /v1/file-transfers/outgoing/{transfer_uuid}`, чтобы
он принимал `urn:sticker:<uuid>`. Сохранить существующие авторизацию назначения,
идемпотентность, транспорт скачивания и оболочку ответа. Для стикеров `file_uuid` —
это UUID каталога, `name` — `<uuid>.<format>`, а размер, хеш и тип описывают
исходное медиа каталога. Использовать только активные стикеры без блокировки в
рамках текущей request session. Sticker URN имеет строгую форму без query suffix.
Все обычные проверки ACL вложений сохранить.

Не нужны синтетический WorkspaceFile, дополнительный endpoint загрузки, публичный
доступ к bucket, новая таблица базы данных или отдельная транзакция запроса.
Проверка каталога заменяет проверку file-sidecar только для sticker URN.
Существующие выдаваемые на ограниченный срок права на один объект используются
повторно. При выдаче нового права видимость проверяется заново; ранее выданные
права сохраняют текущую семантику истечения срока действия.

### Проверка стикера во входящем каталоге

Добавить read-only private endpoint в тот же аутентифицированный bridge service:

`GET /v1/stickers/{uuid}?external_account_uuid=<uuid>&external_chat_uuid=<uuid>`

Обязательные параметры account/chat указывают на назначение, доступ к которому
сейчас разрешён. Для синхронизации истории нельзя создавать исходящую операцию
или выдуманное transfer.

Ответ `200` содержит ровно `uuid`, `sha256`, `size_bytes` и `content_type`.
В нём никогда не бывает storage key, credentials или download URL.
Недоступные и неизвестные записи каталога возвращают `404`, неразрешённые
назначения — `403`. Невалидные входные данные используют существующие ошибки
валидации private API. Временные ошибки service остаются сбоями, для которых
доступен существующий retry flow.

### Markdown-метка

Полная метка ссылки должна быть `workspace-sticker:v1:<uuid>`. Сохранить
существующую структуру bridge `[...]` и `![...]`; не требовать нового уровня
поддержки Zulip Markdown. Только разобранные ссылки на вложения подходят для
метаданных; обычный текст, code spans и fenced code метаданными не являются.

Метка определяет тип вложения, а не автора сообщения или операцию. Она публична
и не является credential для авторизации. Физическое имя загруженного файла не
обязано содержать метку.

## Алгоритм исходящей обработки

1. Разобрать Markdown существующим converter и распознать sticker URN.
2. Авторизовать и скачать исходный объект через расширенный file API.
3. Повторно использовать существующие механизмы загрузки provider и operation/retry.
4. Установить метку вложения в versioned marker и его назначение в путь загрузки
   Zulip из ответа. Остальные элементы сообщения не менять.
5. Сохранить исходный Workspace payload без изменений.

## Алгоритм входящей обработки

1. Разобрать исходный Zulip Markdown через существующий live/history conversion path.
2. Для ссылки загрузки с поддерживаемой меткой прочитать текущие scoped metadata
   каталога и сравнить исходные скачанные байты по SHA-256 и размеру. Никогда не
   хешировать thumbnail; одного provider MIME label недостаточно для доказательства
   идентичности.
3. При подтверждённом совпадении вернуть
   `![sticker](urn:sticker:<uuid>)` без обычного выделения входящего файла и без
   создания записи WorkspaceFile.
4. Без метки, при неизвестной версии, некорректной метке или подтверждённом
   несовпадении продолжить обычный импорт изображения из скачанных байтов. Для
   поддерживаемой корректной метки с недоступным UUID вывести generic-заглушку
   `Sticker unavailable` и не импортировать обычное изображение; deleted,
   missing и blocked состояния намеренно неразличимы.
5. Не превращать ошибку авторизации или временную сетевую ошибку в постоянное
   решение об обычном изображении; сохранить существующее поведение ошибок и
   повторных попыток.

Канонизировать восстановленную метку в `sticker`, чтобы повторная синхронизация
не чередовала разные метки. Отмеченные копии в новых сообщениях Zulip могут стать
стикерами после проверки; они остаются новыми сообщениями, а не эхом исходного.

## Эхо, редактирование и история

Нормализовать вложение перед существующими сравнениями канонического содержимого
и отправкой Provider event. Для дедупликации сообщений продолжать использовать
существующее сопоставление operation/provider identity; метку нельзя использовать
как message ID.

Сохранять настоящие редактирования: при изменении текста совпадающие стикеры
сохраняются; удаление убирает элемент; замена на другие байты или удаление метки
превращает вложение в обычное. Нельзя игнорировать все обновления сообщений,
созданных Workspace. История, доставка второму аккаунту, ранние события и
восстановление после перезапуска не должны зависеть от in-memory outgoing marker
cache. Проверить reconciliation неоднозначной отправки и обычные live events на
использование той же нормализации.

## Ответственность компонентов и зависимости

1. **Медиа и метаданные backend:** scoped resolvers и private endpoints отвечают
   за авторизацию, видимость каталога, доступ к медиа и стабильную схему ответа,
   которую использует bridge.
2. **Преобразование bridge:** file client и outgoing/incoming converters отвечают
   за обработку метки, загрузку provider, проверку байтов, историю и reconciliation,
   сохраняя поведение обычных вложений.
3. **Обработка событий provider:** обновления и межпроектная проекция сохраняют
   канонический sticker URN без поиска обычного WorkspaceFile.
4. **Проверка контракта:** тесты backend и bridge покрывают общую private API
   schema, авторизацию, поведение PostgreSQL, преобразование, retry paths и storage
   adapters. Ручная приёмка Zulip остаётся отдельным доказательством, поскольку
   unit fakes и S3 presign mocks не подтверждают отображение в клиенте и полный
   provider roundtrip.

## Матрица приёмки

| Случай | Ожидаемый результат |
| --- | --- |
| Стикер отправлен из Workspace | Медиа в Zulip; URN стикера Workspace сохранён |
| Собственное echo, дубликат или раннее событие | Нет дубликата; тот же канонический стикер |
| Второй аккаунт или история без send cache | Проверенный стикер восстановлен |
| Те же байты без метки | Обычное изображение |
| Метка с другими исходными байтами | Обычное изображение |
| Неизвестная версия или некорректная метка | Обычное изображение |
| Поддерживаемая метка с недоступным UUID | Generic-заглушка `Sticker unavailable`; без импорта обычного изображения |
| Назначение запрещено | Ошибка авторизации, метаданные каталога не раскрываются |
| Временная ошибка поиска или скачивания | Существующее поведение ошибки и retry |
| Смешанный текст, изображения и несколько стикеров | Порядок и типы элементов сохранены |
| Синтаксис метки внутри code | Буквальный code не изменён |
| Изменение текста, замена или удаление вложения | Фактическое редактирование отражено |
| Стикер заблокирован до нового grant | Новый grant запрещён |
| Перемещение сообщения между проектами | Глобальная ссылка на стикер не изменена |

## Развёртывание и проверка

Автоматизированные тесты, реальные проверки PostgreSQL, проверки с
замокированными provider/storage и ручная приёмка Zulip дают разные доказательства
и фиксируются отдельно. Видимость метки в клиентах Zulip нужно измерить, а не
считать её скрытой.

Сначала разворачивается backend, затем совместимый bridge. Отправка стикеров
остаётся выключенной до развёртывания bridge. UI-действие delete включается
только после развёртывания backend DELETE API.

Приёмка релиза включает реальное отображение в Zulip, поведение сетевых повторов
и полный roundtrip mTLS/S3/provider. Автоматизированные и замокированные проверки
не заменяют эти интеграционные проверки.
