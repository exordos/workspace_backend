# Техническое задание: серверный каталог стикеров

## Статус документа

- Версия: `1.1`.
- Состояние: контракт Gate G0 закрыт; решения `D-01`–`D-14` обязательны для реализации.
- Документ описывает согласованный контракт и не является утверждением, что API уже реализован.

## 1. Цель

Создать серверный каталог стикеров для Workspace Messenger.

Под стикером в этом документе понимается единая сущность каталога, которая может содержать:

- анимированный GIF;
- анимированный или статический WebP;
- статический PNG;
- обычное мемное изображение, используемое в интерфейсе как стикер.

Каталог должен позволять клиентскому приложению:

- получать доступные стикеры;
- искать стикеры по словам и тегам;
- получать конкретные стикеры по устойчивым идентификаторам;
- добавлять стикеры в личное избранное;
- удалять стикеры из личного избранного;
- использовать одну коллекцию избранного во всех проектах пользователя.

Сервер должен позволять уполномоченному администратору:

- импортировать подготовленный набор стикеров;
- изменять название, альтернативный текст, теги и состояние стикера;
- скрывать или полностью блокировать стикер без физического удаления исторически используемого файла.

## 2. Принятые решения

### 2.1. Единая сущность стикера

GIF, WebP и PNG не образуют отдельные каталоги. Формат является характеристикой медиафайла одной общей сущности `sticker`.

В первую версию входят только `gif`, `webp` и `png`. WebM и Lottie откладываются до появления конкретного пользовательского сценария.

### 2.2. Общий каталог

Каталог является общим для Workspace и не принадлежит отдельному пользователю или проекту.

На первом этапе пользовательские наборы, установка наборов и проектные каталоги не предусматриваются.

### 2.3. Глобальное избранное пользователя

Избранное привязывается только к пользователю и стикеру:

```text
user_uuid + sticker_uuid
```

`project_id` в эту связь не входит. Стикер, добавленный в избранное в одном проекте, должен отображаться в избранном этого пользователя во всех остальных проектах.

Идентификатор пользователя определяется сервером из IAM-контекста. Клиент не передаёт `user_uuid` в теле запроса и не может управлять избранным другого пользователя.

Избранное по умолчанию сортируется по времени добавления: недавно добавленные элементы находятся выше. Сервер не хранит частоту и время последнего использования стикера в первой версии.

### 2.4. Разделение S3 и PostgreSQL

S3-совместимое хранилище содержит бинарные объекты. PostgreSQL содержит данные каталога, поисковые поля и пользовательское избранное.

Поиск по содержимому S3 не выполняется.

### 2.5. Устойчивый идентификатор

Клиент и сообщения должны ссылаться на `sticker_uuid`, а не на имя бакета, ключ S3 или временный URL.

Расположение объекта в S3 является внутренней деталью сервера.

### 2.6. Категория и формат

Продуктовая категория и технический формат хранятся раздельно:

- `category = gif` — гифка, мемная или реакционная картинка, обычно анимированная;
- `category = sticker` — самостоятельный стикер, статический или анимированный, с прозрачным фоном или без него;
- `format = gif | webp | png` — фактический формат медиафайла, подтверждённый серверной проверкой.

Категория не определяется автоматически только по формату или наличию прозрачности. Один и тот же формат может использоваться в обеих категориях.

Если категория отсутствует при импорте, сервер устанавливает `category = sticker`. Такое значение является безопасным общим вариантом и не делает предположений об анимации или прозрачности.

Значение `gif` намеренно используется и как продуктовая категория, и как возможный технический формат. Разработчики должны различать поля по их назначению: `category` управляет продуктовой группой «Гифки» или «Стикеры», а `format` описывает фактический формат файла. Например, анимированный WebP может иметь `category = gif` и `format = webp`.

### 2.7. Поисковые теги и данные смайлов

`tags` является свободным массивом слов и коротких фраз для текстового поиска.

`emoji` является небольшим массивом смайлов, сохранённым как задел для будущей группировки. В первой реализации эти значения принимаются при импорте, хранятся в строке стикера и возвращаются клиенту, но не участвуют в поиске, фильтрации или формировании отдельных групп.

Для тегов не используется закрытый справочник или заранее утверждённый список допустимых значений. Новые поисковые теги можно добавлять без изменения схемы базы данных и API.

Технические ограничения на длину одного значения, общий размер массива и размер запроса допускаются для защиты сервера. Они не должны превращаться в ограниченный продуктовый словарь тегов.

### 2.8. Название и альтернативный текст

`title` является коротким названием стикера для каталога и административного интерфейса.

`alt_text` является кратким текстовым описанием того, что изображено и происходит в медиафайле. Клиент использует его как альтернативный текст изображения и доступное название элемента управления, а сервер включает его в текстовый поиск.

Отдельное поле `description` в первой версии не вводится. Если позднее понадобится редакционное описание, отображаемое пользователю отдельно от альтернативного текста, его можно будет добавить независимо.

## 3. Границы первой версии

### 3.1. Входит в первую версию

- общий каталог;
- постраничное получение каталога;
- получение одного стикера;
- пакетное получение стикеров по идентификаторам;
- поиск по названию, альтернативному тексту и тегам;
- личное избранное пользователя без привязки к проекту;
- административный импорт подготовленного архива;
- административное редактирование данных карточки стикера;
- скрытие и полная блокировка стикеров;
- хранение одного медиафайла на стикер без серверного сжатия и создания уменьшенных версий;
- проверка типа, размера, контрольной суммы и основных параметров медиафайла;
- сортировка избранного по времени добавления, от новых к старым.

### 3.2. Не входит в первую версию

- добавление стикеров обычными пользователями;
- пользовательские наборы и коллекции помимо избранного;
- установка и удаление наборов;
- комментарии, оценки и жалобы;
- автоматическая модерация;
- поиск через Elasticsearch или OpenSearch;
- синхронизация избранного с внешними поставщиками;
- фоновое получение каталога GIPHY;
- хранение недавних стикеров на сервере;
- хранение времени последнего использования и счётчика использования стикера;
- ручная сортировка избранного;
- создание уменьшенных версий, статических кадров и других производных файлов;
- сжатие и преобразование медиафайлов на сервере;
- поддержка WebM и Lottie;
- группировка и фильтрация по смайлам;
- постоянный журнал импортов и откат целого импортированного пакета;
- административная панель управления каталогом;
- физическое удаление медиафайлов, которые могли использоваться в сообщениях.

## 4. Схема хранения

### 4.1. Объекты в S3

Зафиксированная схема ключа:

```text
stickers/{sticker_uuid}/media.{расширение}
```

В первой версии для стикера хранится ровно один медиафайл. Этот же файл используется в сетке каталога и в сообщениях.

Сервер не сжимает, не перекодирует и не создаёт производные версии файла. Если файл превышает установленные ограничения, импорт отклоняет его с понятной ошибкой.

Объект должен быть неизменяемым. Существующие local/S3 `save` paths backend допускают overwrite, поэтому будущий sticker storage adapter обязан перед записью отказать при занятом object id либо сделать idempotent no-op только при том же SHA-256. Другой content никогда не перезаписывается. Новая версия файла получает новый ключ или новый идентификатор стикера.

### 4.2. Таблица каталога

Имя таблицы: `m_workspace_stickers`.

| Поле | Тип | Назначение |
|---|---|---|
| `uuid` | UUID | Устойчивый идентификатор стикера |
| `title` | TEXT | Короткое отображаемое название |
| `alt_text` | TEXT | Краткое описание изображения для доступности и поиска |
| `emoji` | TEXT[] | Сохранённые смайлы для возможной будущей группировки; в MVP не индексируются и не используются для фильтрации |
| `tags` | TEXT[] | Нормализованный массив русских и английских тегов |
| `search_text` | TEXT | Подготовленное сервером поле для текстового поиска |
| `category` | TEXT | Продуктовая категория: `gif` или `sticker`; по умолчанию `sticker` |
| `format` | TEXT | `gif`, `webp` или `png` |
| `width` | INTEGER | Ширина медиафайла |
| `height` | INTEGER | Высота медиафайла |
| `size_bytes` | BIGINT | Размер медиафайла |
| `sha256` | TEXT | Контрольная сумма медиафайла |
| `media_object_id` | TEXT | Внутренний ключ медиафайла в хранилище |
| `active` | BOOLEAN | Доступность стикера в каталоге и для новых отправок |
| `blocked` | BOOLEAN | Полный запрет выдачи и отображения медиафайла |
| `created_at` | TIMESTAMPTZ | Время создания записи |
| `updated_at` | TIMESTAMPTZ | Время последнего изменения |

Массивы смайлов и тегов хранятся непосредственно в строке стикера. Отдельные таблицы для них в первой версии не создаются.

База данных ограничивает `category` значениями `gif` и `sticker`, а также запрещает сочетание `active = true` и `blocked = true`.

#### Разница между `uuid` и `media_object_id`

`uuid` является идентификатором сущности стикера. Он используется в публичном API, сообщениях, избранном и связях PostgreSQL.

`media_object_id` является внутренним адресом бинарного объекта в S3-совместимом хранилище. Он не передаётся клиенту и может измениться при переносе данных или изменении схемы ключей без изменения `uuid` стикера.

Пример:

```text
uuid:            7ec10000-0000-0000-0000-00000000009a
media_object_id: stickers/7ec10000-0000-0000-0000-00000000009a/media.gif
```

В первой версии ключ можно формировать по `uuid`, но его значение всё равно сохраняется в строке каталога. Это сохраняет независимость доменной модели от конкретной структуры S3 и соответствует существующему подходу файлового хранилища backend.

### 4.3. Таблица избранного

Имя таблицы: `m_workspace_sticker_favorites`.

| Поле | Тип | Назначение |
|---|---|---|
| `user_uuid` | UUID | Пользователь из IAM-контекста |
| `sticker_uuid` | UUID | Стикер из общего каталога |
| `created_at` | TIMESTAMPTZ | Время добавления в избранное |

Первичный ключ:

```text
(user_uuid, sticker_uuid)
```

Поле `project_id` отсутствует намеренно.

## 5. Доступность и блокировка стикера

В первой версии используются два логических признака: `active` и `blocked`.

### Видимый стикер

```text
active = true
blocked = false
```

Стикер отображается в каталоге, участвует в поиске, может добавляться в избранное и использоваться в новых сообщениях.

### Скрытый стикер

```text
active = false
blocked = false
```

Стикер не отображается в общем каталоге и поиске, не может добавляться в избранное и использоваться в новых сообщениях. При этом он продолжает разрешаться по `sticker_uuid` для уже существующих сообщений, чтобы история не ломалась.

### Заблокированный стикер

```text
blocked = true
```

Стикер не отображается в каталоге, не участвует в поиске и не возвращает медиафайл даже для старых сообщений. Клиент показывает безопасную заглушку.

Блокировка является обратимой. Администратор может использовать её как временную меру на время проверки жалобы или оставить бессрочно. Причина блокировки в первой версии не хранится; при появлении требований к журналу модерации для неё добавляются отдельные поля или отдельная таблица.

База данных должна запрещать сочетание `active = true` и `blocked = true`.

Скрытие или блокировка предпочтительнее физического удаления записи и объекта. Это сохраняет целостность истории, возможность аудита и возможность восстановить доступ.

## 6. Контракт API

Маршруты следуют соглашениям RestAlchemy, уже используемым в Workspace Messenger:

- коллекция и создание ресурса используют путь `/resources/`;
- чтение и изменение отдельного ресурса используют путь `/resources/{resource_uuid}`;
- GET-действие над ресурсом использует путь `/resources/{resource_uuid}/actions/{action}` без суффикса `/invoke`;
- команда, изменяющая состояние ресурса, использует POST-путь `/resources/{resource_uuid}/actions/{action}/invoke`;
- команда над коллекцией использует POST-путь `/resources/actions/{action}/invoke` и отдельный маршрут действий коллекции.

Имена внутренних контроллеров и моделей могут отличаться; форма публичных путей неизменна.

### 6.1. Получение и поиск

```http
GET /api/workspace/v1/messenger/stickers/
```

Поддерживаемые параметры:

| Параметр | Назначение |
|---|---|
| `q` | Текст поискового запроса |
| `favorite` | При значении `true` возвращает только избранное текущего пользователя |
| `uuid` | Повторяемый параметр для пакетного получения по идентификаторам |
| `category` | Необязательная фильтрация по категории `gif` или `sticker` |
| `format` | Необязательная фильтрация по формату |
| `page_limit` | Размер страницы |
| `page_marker` | Маркер следующей страницы |

Обычный список и поиск возвращают только стикеры с `active = true` и `blocked = false`.

`page_limit` принимает целое от 1 до 100, значение по умолчанию — 50. `q` ограничен 200 Unicode code points. Повторяемый `uuid` допускает не более 100 значений. Неизвестные параметры и нарушение лимитов получают стандартную ошибку RestAlchemy `400`.

Для списка без `q` сортировка: `created_at DESC, uuid DESC`; для поиска и `favorite=true` сортировка: `rank DESC, favorite_created_at DESC, uuid DESC` (`favorite_created_at` для не-избранных равен минимальному значению). `page_marker` — opaque base64url без padding с canonical JSON-полями `v`, `sort`, `filters_sha256`, `values`. `values` содержит полную sort tuple. `filters_sha256` — SHA-256 canonical JSON параметров `q`, `favorite`, `category`, `format`, canonicalized `uuid` и сортировки. UUID dedupe-ится и сортируется лексикографически перед fingerprint; допускается pagination с максимумом 100 UUID. Несовпадение fingerprint или версии маркера даёт `400`.

Пакетное разрешение по `uuid` может возвращать скрытые стикеры с `active = false`, чтобы старые сообщения продолжали отображаться. Заблокированные стикеры не возвращаются как доступные медиа.

```http
GET /api/workspace/v1/messenger/stickers/{sticker_uuid}
```

Возвращает один доступный стикер или безопасную ошибку отсутствия ресурса.

```http
GET /api/workspace/v1/messenger/stickers/{sticker_uuid}/actions/download
```

Возвращает необработанные байты медиафайла. Это GET-действие RestAlchemy, поэтому суффикс `/invoke` не используется. Сервер проверяет доступность стикера, находит внутренний `media_object_id` и читает объект из S3-совместимого хранилища. Внутренний ключ S3 клиенту не раскрывается.

### 6.2. Избранное

```http
POST /api/workspace/v1/messenger/stickers/{sticker_uuid}/actions/star/invoke
```

Идемпотентно добавляет стикер в избранное текущего пользователя. Повторный запрос не создаёт дубликат. Форма операции повторяет существующее действие `star` для сообщений.

```http
POST /api/workspace/v1/messenger/stickers/{sticker_uuid}/actions/unstar/invoke
```

Идемпотентно удаляет стикер из избранного текущего пользователя. Отсутствие связи не считается ошибкой. Форма операции повторяет существующее действие `unstar` для сообщений.

Запрос каталога с `favorite=true` по умолчанию сортирует элементы по `created_at` связи избранного в порядке убывания. Отдельных операций для ручной сортировки, фиксации использования или изменения счётчика популярности нет.

### 6.3. Административный импорт

```http
POST /api/workspace/v1/messenger/stickers/actions/import_archive/invoke
Content-Type: multipart/form-data
```

Запрос содержит одно multipart-поле `archive` с ZIP-архивом, подготовленным расширением или другим доверенным инструментом:

```text
archive=@my-stickers.zip
```

`manifest.json` не передаётся отдельным multipart-полем: он находится внутри архива и описывает все вложенные медиафайлы.

Импорт является командой над каталогом, а не созданием сохраняемой сущности `sticker_import`. Поэтому он оформляется как действие `import_archive` над коллекцией `stickers`. Имя действия прямо указывает, что запрос принимает ZIP-архив, и не вводит отдельную сущность пакета.

Операция требует разрешения `workspace.sticker_catalog.manage`.

Успешный ответ (`200`) имеет точную форму:

```json
{
  "created": 12,
  "duplicates": 2,
  "items": [
    {
      "client_id": "20000000-0000-0000-0000-000000000000",
      "file": "media/20000000-0000-0000-0000-000000000000.gif",
      "status": "created",
      "sticker_uuid": "00000000-0000-0000-0000-000000000000"
    }
  ]
}
```

В первой версии обработка архива выполняется синхронно со следующими ограничениями:

- размер ZIP-архива — не более 40 МиБ (`41 943 040` байт);
- не более 50 медиафайлов;
- суммарный размер распакованных файлов — не более 100 МиБ;
- размер одного медиафайла — не более 10 МиБ;
- ширина и высота — не более 2048 пикселей;
- отношение распакованного размера к размеру архива — не более 20:1.

Архив используется только как транспорт пакета и не сохраняется в S3. Сервер распаковывает его во временную директорию, проверяет весь набор и затем загружает каждый медиафайл в S3 отдельным объектом.

Импорт является атомарным на уровне каталога: при ошибке проверки хотя бы одного нового элемента запрос отвечает стандартной ошибкой RestAlchemy `400`, записи каталога не создаются. Дубликаты по SHA-256 не считаются ошибкой и пропускаются. Если ошибка возникает после начала загрузки в S3, сервер удаляет уже загруженные объекты этой попытки. Ошибка SQL или неопределённый исход финального commit не позволяет безопасно утверждать отсутствие DB rows; в этом случае объекты не удаляются автоматически, а повтор запроса разрешается по уникальному SHA и покрывается orphan-repair проверкой.

Постоянная запись о попытке импорта не создаётся. Клиент получает результат текущего запроса и должен явно показать его администратору. Переход к фоновой задаче и журналу импортов допускается позднее без изменения формата архива.

### 6.4. Административное редактирование

```http
PUT /api/workspace/v1/messenger/stickers/{sticker_uuid}
```

Операция требует разрешения `workspace.sticker_catalog.manage` и позволяет изменять только:

- `title`;
- `alt_text`;
- `emoji`;
- `tags`;
- `category`;
- `active`;
- `blocked`.

Замена медиафайла через эту операцию не допускается.

### 6.5. Статусы и ошибки

- `200` — успешный list/get/batch, download, star/unstar и импорт.
- `304` — совпавший `If-None-Match` для JSON списка; тело отсутствует.
- `400` — `ValidationErrorException` RestAlchemy для неверного JSON/multipart, лимитов, фильтров и cursor fingerprint.
- `401` — отсутствие или недействительность IAM-аутентификации.
- `403` — отсутствует `workspace.sticker_catalog.manage` для import/PUT.
- `404` — отсутствующий или заблокированный ресурс; для blocked storage не читается.
- `405` — штатный `UnsupportedHttpMethod` RestAlchemy.
- `409` — только если конкретный DB unique-конфликт не обработан как идемпотентный duplicate.

Ошибки используют стандартный объект `{ "type": "...", "code": ..., "message": "..." }` и не содержат bucket, S3 key или credentials.

## 7. Клиентский контракт

Клиент получает только необходимые для интерфейса поля. Внутренние ключи S3, имя бакета и параметры подключения не выдаются.

Успешный ответ элемента каталога (`200`):

```json
{
  "id": "00000000-0000-0000-0000-000000000000",
  "title": "Одобрение",
  "alt_text": "Мужчина одобрительно кивает",
  "emoji": ["👍", "✅"],
  "tags": ["да", "согласие", "yes", "approval"],
  "category": "gif",
  "media": {
    "format": "gif",
    "width": 240,
    "height": 180,
    "url": "/api/workspace/v1/messenger/stickers/00000000-0000-0000-0000-000000000000/actions/download"
  },
  "is_favorite": true

```

Поле `is_favorite` вычисляется для текущего пользователя.

В первой версии `url` содержит RestAlchemy GET-действие `actions/download`; backend возвращает байты напрямую с `ETag: "<sha256>"` и `Cache-Control: private, max-age=31536000, immutable`. Редирект на подписанный URL не входит в MVP. Клиент не должен сохранять итоговый URL как устойчивую ссылку.

## 8. Поиск

### 8.1. Индексы

- GIN-индекс по `tags` для точного поиска по тегам.
- GIN-индекс с `pg_trgm` по `search_text` для частичных совпадений и простых опечаток.

### 8.2. Нормализация

Сервер перед сохранением:

- удаляет повторяющиеся смайлы и сохраняет их как отдельные значения массива `emoji`;
- приводит теги к нижнему регистру;
- удаляет лишние пробелы;
- удаляет дубликаты;
- нормализует `ё` и `е` для поиска;
- формирует `search_text` из `title`, `alt_text` и тегов.

Клиент не формирует `search_text` самостоятельно.

Теги остаются свободными и не ограничиваются заранее заданным словарём. Значения `emoji` в первой реализации не включаются в `search_text`.

### 8.3. Зафиксированный порядок результатов

1. Точное совпадение тега.
2. Точное или префиксное совпадение названия.
3. Частичное совпадение `alt_text` и общего поискового текста.
4. Нечёткое совпадение через `pg_trgm`.

### 8.4. Контракт решений Gate G0

Технические лимиты: `title` — 200 Unicode code points, `alt_text` — 500, один tag — 64, не более 64 tags, суммарно tags — 4096 UTF-8 bytes, `q` — 200, `page_limit` — 1–100 (default 50), `uuid` — не более 100 значений. Это защитные лимиты, а не закрытый словарь.

Идентификаторы решений: `D-01` — cursor и sort tuple из следующего абзаца; `D-02` — перечисленные лимиты; `D-03` — атомарный `400` без `rejected` в успехе; `D-04` — duplicate по SHA без смены состояния; `D-05` — персональный ETag JSON; `D-06` — immutable media cache; `D-07` — Pillow и фактическая проверка формата; `D-08` — permission `workspace.sticker_catalog.manage` из IAM; `D-09` — request transaction и S3 compensation; `D-10` — hidden только для batch/history; `D-11` — публичный `id`, внутренний `uuid`; `D-12` — storage через `media_object_id`; `D-13` — один UUID на одинаковый SHA внутри ZIP; `D-14` — favorite row сохраняется при hide/block.

Маркер страницы кодируется как base64url без padding от canonical JSON `{ "v": 1, "sort": "...", "filters_sha256": "...", "values": [...] }`. `values` содержит полную sort tuple, последний элемент — UUID. Fingerprint считается от canonical JSON параметров `q`, `favorite`, `category`, `format`, dedupe+lexicographically sorted `uuid` и сортировки. Маркер с другим fingerprint или версией отвечает `400`.

Состояния имеют точную семантику: list/search и item GET показывают только `active=true, blocked=false`; batch resolve также возвращает hidden (`active=false, blocked=false`); download разрешён active и hidden, но blocked отвечает безопасным `404` без обращения к storage. Favorite row не удаляется при hide/block, но фильтр `favorite=true` возвращает только видимое; после unhide/unblock связь снова видна. Star для hidden/blocked запрещён, unstar идемпотентен.

Для проверки GIF/WebP/PNG используется Pillow как единственная библиотека декодирования. Общий dependency-шаг WP-00.1 добавляет её в runtime и lock до начала WP-08. Проверяются сигнатура, фактический формат, `verify()` и размеры до 2048×2048.

Проверка выполняется по байтам: GIF начинается с `GIF87a` или `GIF89a`, PNG — с сигнатуры `89 50 4e 47 0d 0a 1a 0a`, WebP — с `RIFF` в первых 4 байтах и `WEBP` в байтах 8–11. После проверки сигнатуры Pillow открывает файл, его `format` должен совпасть с manifest/расширением, размеры проверяются до `load()`, затем вызываются `verify()` и повторное открытие с `load()` для проверки декодирования. `DecompressionBombError` и `UnidentifiedImageError` превращаются в стандартную ошибку валидации; сервер не доверяет MIME, расширению или размерам из manifest.

## 9. Импорт

### 9.1. Структура ZIP-архива версии 1

```text
manifest.json
media/
  20000000-0000-0000-0000-000000000000.gif
  30000000-0000-0000-0000-000000000000.webp
```

Архив является только транспортным контейнером. Он не сохраняется в S3 целиком. `manifest.json` сохраняется в PostgreSQL не как единый JSON: сервер разбирает его и создаёт отдельную строку каталога для каждого элемента.

Связь между записью JSON и медиафайлом задаётся только полем `file`. Положение элемента в массиве, имя стикера и порядок файлов в ZIP для сопоставления не используются.

`manifest.json` кодируется в UTF-8 и имеет следующую схему:

```json
{
  "schema_version": 1,
  "items": [
    {
      "client_id": "20000000-0000-0000-0000-000000000000",
      "file": "media/20000000-0000-0000-0000-000000000000.gif",
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "format": "gif",
      "title": "Одобрение",
      "alt_text": "Мужчина одобрительно кивает",
      "emoji": ["👍", "✅"],
      "tags": ["да", "согласие", "одобрение", "yes", "approval"],
      "category": "gif"
    }
  ]
}
```

Назначение полей элемента:

| Поле | Обязательность | Назначение |
|---|---|---|
| `client_id` | Обязательно | UUID записи в расширении; используется для связи результата импорта с локальной записью и не становится `sticker_uuid` |
| `file` | Обязательно | Относительный путь к единственному медиафайлу этого элемента внутри ZIP |
| `sha256` | Обязательно | SHA-256 байтов файла в нижнем регистре |
| `format` | Обязательно | Ожидаемый формат: `gif`, `webp` или `png` |
| `title` | Обязательно | Короткое название карточки |
| `alt_text` | Обязательно | Краткое описание содержания медиафайла |
| `emoji` | Обязательно | Массив из 0–5 смайлов, сохраняемый для будущей группировки |
| `tags` | Обязательно | Единый массив русских и английских поисковых тегов |
| `category` | Необязательно | `gif` или `sticker`; при отсутствии сервер устанавливает `sticker` |

Поля `width`, `height`, `size_bytes`, MIME-тип и итоговый `media_object_id` в manifest не передаются. Сервер вычисляет их по фактическим байтам и не доверяет значениям, вычисленным расширением.

`client_id` является транспортным идентификатором. При создании новой записи сервер генерирует собственный `sticker_uuid`, формирует по нему внутренний S3 key и возвращает оба идентификатора в результате импорта.

### 9.2. Правила содержимого архива

- корень содержит ровно один `manifest.json` и каталог `media/`;
- каждый `items[].file` начинается с `media/` и указывает на существующий обычный файл;
- каждый медиафайл указан ровно одним элементом manifest;
- неуказанные медиафайлы и повторяющиеся пути запрещены;
- абсолютные пути, `..`, символические ссылки и вложенные ZIP-архивы запрещены;
- расширение файла должно соответствовать `format`, а фактическая сигнатура файла проверяется отдельно;
- порядок элементов и файлов не имеет значения.

### 9.3. Профиль экспорта Workspace для расширения

Внутренняя модель расширения может оставаться более подробной. При создании ZIP для Workspace она преобразуется в импортный контракт:

| Текущее поле расширения | Поле импорта Workspace |
|---|---|
| `item.id` | `client_id` |
| `item.file` | `file` |
| `item.sha256` | `sha256` |
| `item.mimeType` | `format` после преобразования MIME-типа |
| `item.title` | `title` |
| `item.description` | `alt_text` |
| `item.emotions` | `emoji` |
| `tagsRu + tagsEn + reactions` | единый нормализованный и дедуплицированный массив `tags` |

Короткие значения из `visibleText` длиной не более ограничения одного тега могут дополнительно включаться в `tags`. Объект `pack`, его название, идентификатор, время создания и название генератора в импортный manifest Workspace не включаются. Также в него не попадают поля `source`, `safety`, `confidence`, `durationMs`, `byteSize`, `width`, `height`, сведения о модели и внутренние состояния очереди.

Расширение может продолжать собирать JPEG, MP4 и WebM для локальной библиотеки, но профиль экспорта Workspace версии 1 должен включать только GIF, WebP и PNG. Неподдерживаемые элементы не добавляются в ZIP и показываются пользователю как пропущенные.

Для профиля Workspace расширение формирует путь к медиафайлу по шаблону `media/<client_id>.<format>`. Исходное имя файла не участвует в контракте и не добавляется в `manifest.json`.

### 9.4. Автоматическое дробление большого экспорта

Если выбранный набор не помещается в один допустимый архив, расширение автоматически создаёт несколько независимых ZIP-архивов.

Каждый архив обязан самостоятельно удовлетворять всем ограничениям импорта:

- размер готового ZIP — не более 40 МиБ (`41 943 040` байт);
- не более 50 элементов и соответствующих им медиафайлов;
- суммарный размер всех файлов после распаковки — не более 100 МиБ (`104 857 600` байт);
- размер одного медиафайла — не более 10 МиБ (`10 485 760` байт);
- отношение суммарного распакованного размера к размеру ZIP — не более 20:1.

Расширение не разделяет один медиафайл на части. Элемент, который сам по себе нарушает ограничение одного файла, формата или размеров изображения, не экспортируется и показывается пользователю как пропущенный с конкретной причиной.

Правила дробления:

1. Подходящие элементы упорядочиваются по `client_id`, чтобы одинаковый набор давал одинаковое распределение по архивам.
2. Элементы последовательно добавляются в текущий архив, пока не будет достигнут любой из лимитов.
3. После создания ZIP расширение проверяет фактический размер полученного `Blob`. Если архив превышает 40 МиБ, последний элемент переносится в следующий архив, а текущий архив создаётся повторно.
4. Каждый ZIP содержит собственный `manifest.json` только со своими элементами и собственный каталог `media/`.
5. Между архивами нет общего `pack_id`, имени пакета или другого связывающего объекта.

Рекомендуемые имена файлов:

```text
workspace-stickers.zip

workspace-stickers-001-of-003.zip
workspace-stickers-002-of-003.zip
workspace-stickers-003-of-003.zip
```

Имя ZIP является только удобным локальным именем: backend не извлекает из него данные и не сохраняет его в каталоге.

Архивы загружаются в API по одному. Атомарность действует отдельно для каждого ZIP: ошибка второго архива не откатывает уже завершённый импорт первого. Повторная отправка безопасна на уровне содержимого, поскольку backend распознаёт уже импортированные медиафайлы по SHA-256 и возвращает их как дубликаты.

Перед скачиванием расширение показывает итог экспорта: количество созданных архивов, количество элементов и размер каждого ZIP, а также список пропущенных элементов с причинами.

Если пользователь выбрал удаление локальных файлов или записей после экспорта, расширение применяет эту политику только после подтверждённого успешного скачивания всех созданных архивов. При ошибке или отмене скачивания любой части исходные локальные данные сохраняются, а пользователю показывается незавершённый экспорт.

### 9.5. Проверки импорта

Сервер обязан проверить:

- версию схемы архива;
- форму всех обязательных полей manifest;
- уникальность `client_id` и `file` внутри пакета;
- фактический MIME-тип, а не только расширение;
- допустимый формат;
- предельный размер файла;
- ширину и высоту;
- совпадение SHA-256;
- отсутствие опасных путей внутри архива;
- отсутствие дубликата по контрольной сумме;
- наличие обязательных полей в `manifest.json`.

Проверка всего пакета выполняется до первой записи в PostgreSQL и до первой постоянной загрузки в S3. При ошибке любого элемента новые стикеры из этого пакета не создаются. Дубликаты по SHA-256 не считаются ошибкой: сервер пропускает их и возвращает существующий `sticker_uuid` со статусом `duplicate`.

Доступ к API или возможность скачать файл сами по себе не подтверждают право на повторное размещение. В каталог импортируются только материалы, для которых принято отдельное решение о допустимости хранения и использования.

## 10. Кэширование и доставка

- Медиафайлы являются неизменяемыми и возвращаются с `ETag: "<sha256>"`, `Cache-Control: private, max-age=31536000, immutable` и фактическим `Content-Type`.
- JSON списка возвращается с `ETag: "<sha256 стабильного UTF-8 JSON тела с учётом user_uuid и параметров>"` и `Cache-Control: private, no-cache`; совпавший `If-None-Match` даёт `304` без тела.
- Элементы каталога загружаются постранично.
- Ответ списка остаётся стандартным JSON-массивом RestAlchemy; `X-Pagination-Limit` содержит фактический лимит, а `X-Pagination-Marker` — opaque `page_marker` только при наличии следующей страницы.
- Единственный медиафайл загружается только для видимых элементов интерфейса и видимых сообщений.
- Клиент использует отложенную загрузку, чтобы не скачивать весь каталог сразу.
- Персонализированные ответы с `is_favorite` не должны попадать в общий межпользовательский кэш без корректного разделения по пользователю.

## 11. Безопасность

- Чтение каталога доступно аутентифицированным пользователям Workspace.
- Избранное всегда ограничено текущим IAM-пользователем.
- Импорт и редактирование требуют отдельного административного разрешения.
- Сервер не принимает `user_uuid` для операций с избранным от клиента.
- Сервер не возвращает внутренние ключи S3 и параметры доступа к хранилищу.
- Архив распаковывается только после проверки путей и лимитов.
- Тип и параметры медиа определяются по фактическому содержимому.
- Значения смайлов и тегов имеют технические ограничения по длине и общему размеру запроса. Справочник допустимых тегов не вводится.

## 12. Связь с сообщениями

Стикер передаётся как обычное сообщение с полезной нагрузкой вида `markdown`. В первой версии отдельный `payload.kind` для стикера не вводится.

Каноническое содержимое сообщения со стикером:

```json
{
  "kind": "markdown",
  "content": "![sticker](urn:sticker:00000000-0000-0000-0000-000000000000)"
}
```

URN содержит устойчивый `sticker_uuid`. Клиент распознаёт такое содержимое как стикер, получает актуальные данные из каталога и отображает специализированное представление вместо обычного Markdown-блока.

Сообщение не сохраняет S3 key или временный URL. Скрытие, блокировка или перенос медиафайла поэтому не требуют изменения уже отправленных сообщений.

## 13. Соответствие текущей архитектуре

- Маршруты размещаются в пространстве `/api/workspace/v1/messenger/`.
- Контроллеры следуют существующему стилю RestAlchemy.
- Валидация полей выполняется доменными моделями, если она относится к самой модели.
- Сложный поиск и пользовательская выборка реализуются через отдельный серверный слой хранения.
- Существующую S3-конфигурацию можно переиспользовать, но каталог не следует представлять как набор пользовательских `WorkspaceFile` с проектными ACL.
- Миграции создаются штатными средствами RestAlchemy и содержат необходимые ограничения, внешние ключи и индексы PostgreSQL.

## 14. Отложенные вопросы

Эти вопросы не блокируют первую версию:

1. Появится ли после первой версии конкретный серверный или межклиентский сценарий, который оправдает отдельный `payload.kind = sticker` вместо существующего Markdown-маркера?
2. Когда потребуется административная панель и нужна ли в ней загрузка одиночного файла помимо ZIP-архива?

## 16. Отложенная возможность: группы смайлов

Группы смайлов не входят в первую реализацию и не должны разрабатываться в рамках MVP. В частности, первая реализация не содержит:

- параметра фильтрации `emoji`;
- маршрута `GET /api/workspace/v1/messenger/sticker_emoji_groups/`;
- отдельного GIN-индекса по смайлам;
- вкладок или быстрых групповых фильтров по смайлам на клиенте.

Для первой реализации достаточно текстового поиска по названию, альтернативному тексту и свободным тегам.

При этом массив `emoji` сохраняется в таблице каталога, передаётся в `manifest.json`, доступен для административного редактирования и возвращается в клиентском JSON. Это пассивные данные на будущее: первая реализация не использует их для поиска, фильтрации, сортировки или построения интерфейса групп.

Если после MVP быстрые группы понадобятся, можно задействовать уже сохранённый массив `emoji`, добавить точный фильтр каталога, read-only ресурс со списком доступных групп и отдельный индекс. Порядок групп в интерфейсе при этом может задаваться клиентом.
