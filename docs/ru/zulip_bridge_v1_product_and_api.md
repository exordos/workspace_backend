## 1. Цели

- Пусть пользователь Workspace подключает один личный аккаунт Zulip в области.
- Проект выбрал Zulip разговоры в обычных Workspace потоков и
  темы без создания отдельной внешней поверхности продукта входящего почтового ящика.
- Обеспечьте двустороннюю синхронизацию для набора возможностей V1.
- Сохранить каноническую Workspace архитектуру: PostgreSQL хранит каноническую
  сообщение и данные событий Messenger; файлы используют хранилище объектов и сообщения
  Содержат только URN.
- Сохраните провайдер моста независимо развертываемый и предотвратить его от чтения
  не связанные Workspace строки базы данных или S3 объекты.
- Храните учетные данные провайдера зашифрованными в состоянии покоя и недоступными для браузеров,
  Администраторы, журналы и обычные Workspace API ответы.
- Сделайте нативные сообщения Workspace продолжают работать, когда мост не работает.

  `/providers/` и `/external_users/`.

## 3. Одобрённое поведение продукта

### 3.1 Владение счетом и жизненный цикл

- Внешняя учетная запись принадлежит одному пользователю Workspace и является глобальной для
  что пользователь в пределах сферы.
- У пользователя может быть не более одной внешней учетной записи типа провайдера.
  означает не более одного счета Zulip.
- Zulip настройка требует сервера HTTPS URL, адреса электронной почты и ключа API.
- Достоверные данные только для записи. API может сообщить, что данные существуют, но
  никогда не возвращает ключ API или зашифрованный конверт учетных данных.
- `Disconnect` останавливает синхронизацию, сохраняя только для чтения проекцию.
- `Delete` удаляет учетные данные, отображения, проектируемые объекты, очередную работу,
  и копированные файлы, принадлежащие поставщику.
- IAM деактивация приостанавливает синхронизацию и скрывает учетную запись. IAM удаление.
  очищает его с помощью той же деструктивной семантики, что и `Delete`.

### 3.2 Выбор чата и назначение проекта

- Владелец может выбрать отдельные внешние чаты или выбрать `all`.
- `all` динамичен: чаты, созданные позже, выбираются автоматически.
- Владелец выбирает глубину истории для учетной записи: `new`, `7_days`,
  `30_days`, `90_days`, или`all`- По умолчанию это ...`30_days`.
- Каждый выбранный внешний чат принадлежит ровно одному Workspace проекту.
- У аккаунта есть проект по умолчанию для недавно выбранных чатов.
- Перемещение существующей проекции в другой проект является атомным от продукта
  перспективный и сохраняет Workspace UUID, историю, состояние чтения и провайдера
  Внедрение должно выражать удаление источника проекта и
  Снимок создания целевого проекта; он не должен раскрывать промежуточное состояние
  в которых прогноз не относится ни к одному из проектов, ни к обоим проектам.

### 3.3 Картирование Zulip-Workspace

| Zulip  | Workspace проекция                                                        |
| ------------- | --------------------------------------------------------------------------- |
| Канал       | Поток                                                                      |
| Тема         | Тема в прогнозируемом потоке                                               |
| 1 к 1 DM | Частный личный поток с точно двумя участниками и одной темой по умолчанию |
| Группа DM      | Частный поток группы с одной темой по умолчанию                                 |
| Zulip пользователь    | Стабильная идентификация, разделенная по области поставщика и идентификатору пользователя поставщика                |

Канонический ключ идентификации `(провайдер, provider_realm_uuid,
provider_user_id) `. Область UUID и аутентифицированный идентификатор пользователя аккаунта поступают от
регистрация в очереди на события Zulip, поэтому изменился сервер URL, адрес электронной почты,
показывают имя, или другой аккаунт Workspace не может безмолвно менять владельца.
Совпадения по электронной почте и имени никогда не принимаются в качестве доказательства.

Когда пользователь IAM успешно подключает аккаунт Zulip, только тот, который был аутентифицирован
каноническая идентичность счета Zulip связана с владельцем счета IAM UUID.
Другие Zulip пользователи остаются только для чтения внешние идентификаторы, но повторно использовать один канонический
Workspace UUID через каждый связанный счет в том же Zulip области.
Конфликтная проверенная связь владельца отклонена без изменения одной из идентичностей
и требует явной административного решения.
идентичности объединяются в каноническую идентичность с их Messenger
ссылки, назначения и кэшированные полезные нагрузки событий обновляются до дубликата
Связывание идентификации с IAM не дает этому пользователю доступа к
Прогноз, который принадлежит другому владельцу; только прогноз, принадлежащий владельцу
связанный IAM учетный запись вносит потоки и нечитаемый состояние этого пользователя.
продолжать использовать `urn:user:<identity-uuid>`.

### 3.4 Семантика синхронизации

- V1 поддерживает двустороннее создание, редактирование, удаление, реакции, чтение состояния, упоминания,
  Ответы, цитаты, Маркаdown, ссылки, изображения, файлы и поток/topic переименовать, где
  возможности поставщика позволяют это.
- Входящие операции используют личный счет Zulip владельца.
- Возможности провайдера авторитетны. Неподдерживаемые действия скрыты;
  Временно недоступные действия отключены с безопасным объяснением.
- Последнее подтвержденное действие побеждает. Удалить победу при одновременном редактировании.
- Каждая операция имеет стабильные UUID и провайдерские идентификационные метаданные.
- Успешный результат нативного `message.create` содержит назначенный провайдером
  идентификатор сообщения. Workspace сохраняет эту привязку до импорта echo от
  провайдера, поэтому все подключённые аккаунты одной Zulip-области видят одно
  каноническое сообщение с исходным автором.
- Сначала начинается синхронизация в режиме реального времени и имеет
  строгое планирование приоритета над повторными попытками и заполнением.
- Первоначальное догоняние не создает уведомления для рабочего стола.
  Включается только после того, как аккаунт достиг состояния готовности к работе.
- Каждый признанный поставщик хранит вход `delivery_class` и
  замороженное `notification_eligible` решение в метаданных своего публичного поставщика.
  `backfill` всегда не подлежит учету. Сообщение `live` подлежит учету только тогда, когда
  Вход в систему уведомления о счете был уже открыт при входе; сообщение в режиме реального времени
  Принято, пока история учетной записи все еще набирает обороты, остается не уведомляемым.
  Последующие изменения состояния учетной записи никогда не продвигают сохраненные сообщения ретроактивно.
- Прочный выходной ящик сохраняет перепробованные операции до 24 часов.
  показывает `pending`, то либо `delivered` или `failed`.
  быть повторно опробованными или отброшенными.
- Отмена выбора или потеря доступа к провайдеру отменяет ожидаемую работу и немедленно
  удаляет проекцию и копируемые файлы провайдера.
- Целевая задержка системы p95 не больше 5 секунд.
  `degraded` через 30 секунд без прогресса синхронизации.

### 3.5 Конверсия контента с учетом потерь

- Поддерживаемый Zulip контент конвертируется в канонический Workspace Markdown.
- Не поддерживаемые входящие элементы используют безопасный, читаемый резервный и
  `Open original` связь, когда Zulip может обеспечить один.
- Идентификаторы поставщиков и структурированные метаданные конверсии хранятся в внутренних
  метаданные проекции, не отображаемые в виде записываемых полей браузера.
- Перед выходящей операцией, которая, как известно, теряет информацию, пользовательский интерфейс получает
  результат предлетного полета с серверной стороны и требует ясного подтверждения.
- Приложения копируются в принимающую систему. Workspace
  байты плюс JSON боковой вагон в S3 совместимом хранилище; сообщение содержит только
  `urn:*` ссылки.

### 3. 6 Применение

- Владелец аккаунта видит аккаунт, выбор чата, прогресс, возможности и
  безопасное состояние ошибки для своего собственного счета.
- Администратор области управляет политикой провайдера, пользовательскими сертификатами CA,
  ограничения, а аварийные действия приостанавливаются/resume.
- Администратор области видит только состояние совокупного моста/account.
  поверхность не должна раскрывать учетные данные, содержание сообщения или чат владельца
  Каталог.
- Выходящий Zulip TLS использует хранилище доверия системы плюс управляемый администратором
  проверка хост-названия всегда включена; небезопасно
  или режимы проверки пропусков запрещены.

Внедрение должно продлить текущий контракт Messenger вместо
Возрождение исторического кодекса интеграции.

- Браузерные API остаются под `/api/workspace/v1/messenger/**` и используют IAM
  Токен в настоящее время предоставляет пользовательский UUID и идентификатор проекта.
- Маршруты управления поставщиками остаются дополнением к текущему контракту браузера.
- PostgreSQL является авторитетным для сообщений, состояния обмена Messenger, учетной записи
  настройки, зашифрованные учетные данные, очереди поставщика и записи об устранении дублирования.
- Копирование файлов использует отдельную узкую бинарную плоскость передачи; оно не может предоставить
  глобальные S3 учетные данные моста.
- Поля "публичные" `provider` и "публичные" `delivery` зарезервированы, но не заполнены
  Сериализатор паритет является необходимым условием
  за включение функции.
- Курсоры событий браузера являются проектными и пользовательскими с конфигурируемыми
  Они не являются курсорами мостовой очереди и должны быть
  не могут использоваться в качестве выходной ящика поставщика или позиции для заполнения.
- Текущий остаток `ExternalAccount` является проектным и позволяет простой текст
  JSON учетные данные. Он должен быть заменен на область-объем модели; это не
  Цель миграции или договор о совместимости.

### 5.1 Внешние счета

| Метод   | Маршрут                                                         | IAM разрешение                            | Цель                                                                      |
| -------- | ------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- |
| `GET`    | `/external_accounts/`                                         | `workspace.external_account.read`         | Перечислите внешние учетные записи текущего пользователя.                      |
| `POST`   | `/external_accounts/`                                         | `workspace.external_account.create`       | Создать и подтвердить любой поддерживаемый тип учетной записи с учетными данными только для записи. |
| `GET`    | `/external_accounts/{account_uuid}`                           | `workspace.external_account.read`         | Получи снимки очищенных счетов владельца.                                  |
| `PUT`    | `/external_accounts/{account_uuid}`                           | `workspace.external_account.update`       | Заменить изменяемые несекретные настройки.                                         |
| `POST`   | `/external_accounts/{account_uuid}/actions/reconnect/invoke`  | `workspace.external_account.reconnect`    | Проверьте и замените учетные данные только для записи, а затем продолжите.                 |
| `POST`   | `/external_accounts/{account_uuid}/actions/disconnect/invoke` | `workspace.external_account.disconnect`   | Остановите синхронизацию и сохранить проекцию только для чтения.                                 |
| `DELETE` | `/external_accounts/{account_uuid}`                           | `workspace.external_account.delete`       | Разрушительно очистить счет и вернуть `204`.                            |

Утвержденная форма ресурса - это общая оболочка с динамическим `settings`
`settings.kind` дискриминатор выбирает конкретный
`AbstractKindModel` через
`KindModelSelectorType`Общий жизненный цикл, владелец, статус, пересмотр, возможности,
и полям временной метки остаются за пределами `settings`.
API навязывает, что один
владелец имеет не более одного счета для каждого `settings.kind` в области.

Общественное поле `capabilities` - это фактический уровень учетной записи, рассчитанный в бакенде
Проекция по провайдеру, мостовой инстанции, политике области и отчетности счета
Это не сырой декриптор сердечного ритма и не показывает ни
В интерфейсе пользователя используется это поле для
действия и статус на уровне счета.

Общественные возможности используют карту с того же стабильного имени с пространством имен
к эффективному дескриптору, содержащему `available`, `revision`, `limits`, и
неотложный структурированный сейф `unavailable_reason`.
Временное отключение по состоянию счета или политики остается в наличии с
`available=false`; отсутствие имени означает, что ресурс не поддерживает
Клиенты не должны восстанавливать доступность из сырого состояния или
Провайдер, когда существует эффективный описатель.

Выборчики настроек создания, очистки и восстановления связи различны
API типы. тип create/reconnect может содержать поля учетных данных, предназначенные только для записи;
Соответствующий тип ответа не может их сериализировать.
Календарь, или другой поставщик означает регистрацию новых моделей типа настроек в
выборщики без изменения маршрутов сбора или добавления нулевых полей в

### 5.2 Каталог и назначение внешнего чата

Утвержденный каталог формы является общим ресурсом верхнего уровня Messenger.
доступны только для типов счетов, которые рекламируют возможность `chat_catalog`;
для его реализации не требуется такой тип учетной записи, как почта или календарь.

| Метод | Маршрут                                                 | Цель                                                                |
| ------ | ----------------------------------------------------- | ---------------------------------------------------------------------- |
| `GET`  | `/external_chats/?external_account_uuid=...`          | Перечислите каталог чат-провайдера и статус назначения. |
| `GET`  | `/external_chats/{chat_uuid}`                         | Сделайте одно очищенное видео.                                       |
| `POST` | `/external_chats/{chat_uuid}/actions/select/invoke`   | Выберите чат и назначите проект.                                    |

## 9. Бинарный самолет передачи файлов

Мост не может использовать MIME приложения и не может принимать S3
Утвержденная граница бинарного перевода является отдельным внутренним mTLS
файл API с кратковременными URL-адресами, предварительно обозначенными одним объектом.

Входящий поток файлов провайдера:

1. Мост запрашивает распределение с внешним аккаунтом UUID, чатом UUID,
   операцию UUID, название, размер, тип контента и ожидаемый хэш.
2. Задней части проверяет назначение и возвращает кратковременный пресигнализованный URL
   что позволяет `PUT` для одного объекта.
3. Мост загружает байты и завершает звонки.
4. Задней части проверяет размер и хэш, атомно создает JSON боковой вагон и
   текущий ACL, выполняет проекцию файла и возвращает Workspace URN.

Выходящий Workspace поток файлов:

1. Мост представляет авторизованный Workspace URN, внешний счет UUID,
   chat UUID и операция UUID.
2. Задней панелью пересчитывается текущий доступ от задания чата/stream и
   возвращает кратковременный предписанный `GET` URL для именно этого объекта.
3. Мост загружает байты и копирует их в хранилище провайдера.

Мост не может создавать или изменять боковые вагоны и ACL, перечислять ведро или повторно использовать
a URL для другого объекта.
немедленно удаляет копированные файлы, принадлежащие поставщику, когда проекция удаляется.

Предоставленные `PUT` и `GET` URL-адреса истекают через пять минут.
завершение требует заявленного размера, типа содержимого и SHA-256; завершение не удается
При этом, если в случае несовпадения, то ипотека /finalize является идемпотентной для того же
Идентификация операции и файла, а также истекшие неоконченные распределения удаляются
Работающий в уборке.

Эта служба разрешает только байты бинарного файла; байты перемещаются непосредственно между
Текст сообщения, метаданные и события используют
private Provider HTTP API, и полученное сообщение содержит только возвращенный
URN.

## 10. Граница хранения и развертывания

### Workspace бэк-энд

- Новый внешний аккаунт с охватом сферы, зашифрованные учетные данные, распределение чатов,
  Картографирование поставщика, желаемое состояние/actual и внешние прогнозы операций.
- Стабильная область /installation UUID.
  В данной базе данных уникальность равна `(owner_user_uuid, provider_kind)`.
- Координатор проекта, который пишет канонический старый проектный журнал/new
  переходы при сохранении UUID-ов объектов.
- IAM согласование жизненного цикла в дополнение к текущему обнаружению ленивых пользователей.
- Частный контроль mTLS, провайдер-данные и конечные точки файлов.
- Общественные сериализаторы, которые сохраняют `provider` и `delivery` для потоков,
  темы, сообщения, файлы и вторичные проекции.

### `workspace-zulip-bridge` элемент

Мост - это новое хранилище и независимый элемент Exordos с одной VM,
Заменяемый корневой диск и один постоянный диск данных.
Маршрут открыт.

Устойчивое состояние включает:

- версии ключей шифрования, связанных с областью, и идентификация системы управления;
- длительный выходной ящик/inbox и провайдер HTTP;
- Zulip идентификаторы очереди и курсоры;
- Отнесение поставщика к Workspace и прогресс заполнения;
- аренды планов и отчеты о фактическом состоянии.

Для целевого профиля 1000 аккаунтов, 50 000 чатов, 50 миллионов прогнозируемых
и 100 сообщений/second, операционный магазин должен быть локальным
crash-safe PostgreSQL на постоянном диске.
каноническое состояние Workspace PostgreSQL и S3.

Мост использует справедливый график с строгим приоритетом, затем перепробованный
Zulip ограничения ставки являются авторитетными.

### Безопасные обновления

- Workspace и мостовые элементы обновляются.
  разобраны или недавно перемещены на рабочую установку.
- Каждое изображение разработки использует новую неизменную версию.
- Сохраняется постоянная идентификация диска, вывод узла, порядок диска и ярлыки данных
  стабильный на протяжении всех обновлений.
- Bootstrap не удается закрыть при отсутствии несоответствия состояния ключа /partial или области.
- Очереди, отображения и локальная база данных должны восстановиться после жесткой остановки виртуальной машины,
  Потому что текущая замена изображения ядра не гарантирует грациозное отключение.
- Активация этапируется и ограничена возможностями: API-расширения и мостик
  развернуты с поставщиком типа инвалидов, затем запись, здоровый сердцебиение,
  и требуемые возможности пересечения проверяются перед администратором области
  позволяет Zulip.
- Rollback приостанавливает синхронизацию с провайдером и сохраняет длительные очереди и
  Это не удаляет элемент, удаляет постоянный
  состояние, или прервать нативные сообщения Workspace.

   авторизация примитивная, частный контроль и провайдер-данные OpenAPI, и
   схему шифрованного конверта.
2. **Workspace модель данных**: заменить прежнее остаток счета, охваченного проектом;
   реализация зашифрованных учетных данных, назначения, отображения, состояния операции,

   требуется мостовым элементом.
4. **Проекция и паритет в реальном времени**: заполнить поставщика/delivery метаданных,
   внешние идентификаторы, события полного снимка, поведение перезагрузки кэша, и
   Уведомление о входе.
5. **Основание элемента моста**: создать отдельное хранилище, манифест,
   постоянная загрузка, безопасная от сбоев эксплуатация PostgreSQL, регистрация в mTLS,
   и сглаживание.
6. **Zulip соединитель**: подтверждение учетной записи, каталог, живая очередь, долговечный почтовый ящик,
   Новейшее первое заполнение, конверсия, правила конфликта и справедливый уровень ограничения
   планирование.
7. **UI**: нормализованный домен первого кэша, мастер подключения, выбор/project
   потоки, значки/popovers, внешние идентификаторы, возможности, предлетные и
   повторить /discard поведение.
8. **Принятие**: испытания контракта, интеграция реального поставщика HTTP и Zulip,
   файл ACL испытания, восстановление при столкновении /root-replacement, испытания нагрузки, безопасный элемент
   обновления, и полное видимое согласие драматурга.
