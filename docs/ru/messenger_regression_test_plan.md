# Messenger План испытаний регрессии

Этот план проверяет, что PostgreSQL является каноническим Messenger хранилище, в то время как
текущее поведение файлов API и S3, обращенных к браузеру, остается неизменным.
также определяет восстановление, восстановление, масштабирование и приемку нагрузки.

## Правила приема

- REST пути, органы запроса и ответа, коды состояния, разделение страниц, фильтры,
  правила видимости, и полезные нагрузки событий соответствуют установленным Messenger
  исходный показатель.
- `/api/workspace/v1/messenger/**` остается общедоступным Messenger REST пространством имен;
  Старые `/api/messenger/**` пути остаются отсутствующими.
- REST и события веб-сокета равны после декодирования JSON и остаются охваченными
  аутентифицированный пользователь и проект IAM.
- PostgreSQL хранит канонические Messenger ресурсы, состояние, события и провайдера
  В процессе выполнения чтения и записи не используются SMTP, IMAP, Maildir, Exim или
  Голубиный.
- Файлы, метаданные, боковые вагоны и двоичный доступ продолжают использовать S3-совместимые
  Сообщения содержат только авторизованные URN.
- Провайдеры время выполнения обмениваются обычные Messenger ресурсы и команды через
  частный Workspace провайдер API и никогда не подключаться к Workspace
  База данных.
- Только записи событий хранятся на конфигурированном интервале, 72 часа
  По умолчанию. Сообщения, файлы, потоки, темы, настройки и отображение провайдера
  остаются каноническими, пока их нормальный жизненный цикл не удалит их.

## Окружающая среда испытания

- Изолированный Workspace бэк-энд с свежей PostgreSQL базы данных и все
  миграции.
- S3 - совместимое хранилище объектов, предназначенное для испытания.
- Два IAM пользователя в одном проекте и один IAM пользователь в другом проекте для
  минимальный функциональный ход; полный профиль нагрузки определен в PostgreSQL
  Канонический план.
- Один независимый развертываемый Zulip провайдерный время выполнения и выделенный Zulip
  тестовая область для сценариев поставщиков.
- Одно видное глобальное окно Playwright MCP с использованием реального аккаунта `cassi` для
  видимой приемлемости.

| Идентификация | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| MSG-API-001 | Запросить каждое собрание и действие Messenger ниже `/api/workspace/v1/messenger`. | Методы, коды состояния, схемы, pagination и пути действия соответствуют базовой линии. |
| MSG-API-002 | Запрос `/api/workspace/v1/messenger/server_settings` с последней строкой и без нее, затем разворачивайте и получайте цель `realm_icon` без учетных данных. | Общественный ответ содержит `urn:url:<realm>/logo-512x512.png`, а эмблема упакованной организации возвращается анонимно как `image/png`. |

## Приказ о исполнении

1. Запустить неизмененный блок Messenger и пакет интеграции.
2. Запустить маршрутизацию, OpenAPI, IAM, событие, поставщика API и S3 контрактные тесты.
3. Применение неизменного обновления бэк-энда при сохранении данных PostgreSQL и S3.
4. Использовать Messenger API, провайдер, хранилище, перезагрузка, перестройка, сбой, и
   сценарии изоляции.
5. Исполнение поддерживаемых путешествий в видимом глобальном браузере Playwright MCP.
6. Исполнение 150-равновременных пользовательских нагрузок и рабочей нагрузки провайдера.
7. Сохранить очищенные доказательства в архиве CASSI тестов.

Запуск принимается только после того, как все требуемые сценарии пройдут.
выполненное является `NOT RUN` или `BLOCKED`; оно не должно быть сообщено как проверенное
совместимость.
