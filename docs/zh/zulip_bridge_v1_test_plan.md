# Zulip V1桥试验计划

这一计划是提供者中立的可执行接受门 Workspace
通过外来账户边界和其首次实施`zulip`.
归归计划 Messenger;原生消息, IAM,实时,以及 S3
应在整个运行过程中保持绿色.

常规 Messenger资源和提供商命令生活在 PostgreSQL 中,并且是
通过私人 Workspace 提供商 API 交换.
装载门和回收门
[`messenger_regression_test_plan.md`](messenger_regression_test_plan.md).

## 需要的环境

- Workspace后端更新了其正规的 PostgreSQL 和 S3 数据
  保存的
- 一个独立更新的`workspace-zulip-bridge`节点,可替换
  根盘和一个持久的运行数据盘.
- 专用Zulip测试领域,至少有四个用户,一个频道有两个
  个人DM,团体DM,以及适合两方向的文件.
- 兼容 S3 的 Workspace 存储和私有 Workspace 提供商 API.
- 在可见的剧作家 MCP窗口中正常的 `cassi` Workspace 帐户.
- 五个国家都在外界整合IAM允许资源和既预定义
  角色从Workspace元素显示调和. 绑定所需的角色
  现在`cassi`只有在Workspace试验项目完成IAM它们是普通的.Workspace
  角色不能隐含地获得这些权限.

## 确定性可见UI装置

创建每个固定装置具有独特的运行后,并记录其生成的 UUID 在
保存 Workspace 和 Workspace 两个.
Zulip 开放在独立的可见剧作家 MCP 标签整个旅程.
主要 Workspace 会话始终是真实 `cassi` 帐户;可一次性使用的用户
只有在多用户和破坏性生命周期的情况下进行.

### 账户和项目

| 固定装置                                   | 要求状态                                                                                                 | 目的                                                                     |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Workspace `cassi`                         | 具有外部提供者策略权限和两个测试项目的会员权的活跃领域管理员. | 主持人,普通 Workspace UI 会议,政策/health 接受.     |
| Workspace 同级 A 和同级 B               | 在两项试验项目中,积极的普通用户.                                                                   | 基于本地消息的回归和参与者/unread检查.                  |
| Workspace 生命周期所有者                 | 活跃的普通用户,有独立的 Zulip 帐户.                                                    | IAM 关闭/delete测试,而不会破坏主要`cassi`会话. |
| Zulip 拥有 `cassi` 的所有者                   | 活跃的人类帐户,具有API密钥.                                                                          | 个人外部账户用于主要双向旅行.                |
| Zulip 同级 A,同级 B,以及生命周期主 | 活跃的人类账户.                                                                                         | 个人DM,组DM,提及,更名,以及帐户生命周期的固定.     |
| Workspace项目A和项目B         | 两者都可见到`cassi`;两者都没有包含已有的外部投影.                                   | 核项目开始接受.                      |

不要在 Workspace 所有者之间重复使用 Zulip API 键.存储生成
只有在批准的秘密存储中使用,并移除或旋转一次性
跑步后的钥匙.

### Zulip对话和内容矩阵

| 固定装置            | 连接前需要的内容                                                                                              | 目的                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 频道A          | 主题 `live` 和 `history`;消息更新7天,7至30天,30至90天,90天以上. | 显式选择,每一个历史深度的边界,最新的先排,频道/topic投影.                |
| 频道B          | 至少一个主题,并且在首次连接帐户时没有Workspace投影.                                             | 检查明确排除,然后选择和项目分配.                                                 |
| 频道C          | 只有在 `selection_mode=all` 活跃后才创建.                                                                                | 验证动态发现和自动分配到默认项目.                                         |
| 个人DM        | Zulip 业主和同行A,每个方面至少有一个消息.                                                               | 只有两个参与者和一个默认主题.                                      |
| 组DM           | Zulip 业主,同行A,同行B,每个参与者至少发出一个消息.                                               | 具有一个默认主题和稳定的外部身份的私人组流.                                       |
| 收到的文件     | 一个小的 PNG 和一个非图像文件在B频道中,已知名称,大小, MIME类型和哈希.                              | 提供者到Workspace复制,图像染,通用下载, URN 仅消息内容,以及删除选择清理. |
| 出发文件     | 一个小的 PNG 和一个非图像文件通过 Workspace 编曲器选择.                                                   | 提供者对 Workspace 副本和提供者侧字节/content验证.                                           |
| 损失意识信息 | 包含一个支持的元素和一个未支持的提供者元素的标记,这些元素涵盖了飞行前.                            | 安全后备, `Open original`,损失总结,取消,并明确确认.                                  |

让A频道在历史深度的说法中保持沉默.
只有在预期的后填量和排序被捕获后,
所以一个新的消息不能使一个边界断言模糊.
